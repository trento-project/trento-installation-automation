= Trento Installation Automation

Automated testing infrastructure for Trento release candidate artifacts. This tool is used to provision Azure VMs and install Trento using the official Ansible collection to validate RPM packages before release on supported versions of SUSE SLES for SAP.

== Overview

The workflow:

. Provision one Azure VM per supported SLES version using Terraform
. Register SUSE machines and activates required modules
. Configure package sources from Azure Blob Storage or the Trento rolling repository from https://build.opensuse.org/project/show/devel:sap:trento:factory[OBS]
. Set up a local RPM repository on each machine when using packages from Azure Blob Storage
. Install the Trento Ansible collection on each machine
. Configure HTTPS certificates signed by a test certificate authority
. Run the `suse.trento.site` Ansible playbook to install Trento & Trento agent (Agents are installed on same machine as Trento server).
. Verify Healthcheck endpoints in every Trento instance from the runner
. Run Cypress end-to-end tests against every machine

== Infrastructure

The infrastructure consists of a single VM per supported SLES version. Each
machine runs the `suse.trento.site` playbook against itself: its Ansible
inventory contains only its own public FQDN, reached over SSH.

VM naming convention: `+trento{slesVersion}sp{spVersion}+`

Example: `trento15sp6` for SLES 15 SP6.

== Prerequisites

=== Azure Blob Storage Structure

The RPMs under validation are only reachable from the internal network, so they are downloaded and uploaded to Azure Blob Storage manually, over VPN. There is no automated upload step: the workflow assumes the container is already in the desired state when it starts.

RPMs must be uploaded to Azure Blob Storage with the following structure:

----
<container>/
├── 15/
│   ├── 4/
│   │   ├── trento-web-*.rpm
│   │   ├── trento-wanda-*.rpm
│   │   ├── trento-checks-*.rpm
│   │   ├── trento-agent-*.rpm
│   │   └── ansible-trento-*.rpm
│   ├── 5/
│   │   └── ...
│   └── 6/
│       └── ...
└── 16/
    └── 0/
        └── ...
----

The directory structure follows the pattern: `<sles_major_version>/<sp_version>/`

Each version directory should contain:

* `trento-web-*.rpm` - Trento web server
* `trento-wanda-*.rpm` - Trento checks engine
* `trento-checks-*.rpm` - Trento checks catalog
* `trento-agent-*.rpm` - Trento agent
* `ansible-trento-*.rpm` - Ansible collection for Trento installation

NOTE: When `package_source` is set to `blob_storage` (the default), packages available in Azure Blob Storage are configured with the highest repository priority, and any package missing from it is installed from the official SUSE release sources instead. See <<Choosing which packages to test>> for how to use this to validate a partial release. When `package_source` is set to `rolling`, the Trento rolling repository from https://build.opensuse.org/project/show/devel:sap:trento:factory[OBS] is configured with the highest repository priority and Azure Blob Storage is skipped.

===== Test certificate authority

`TRENTO_TEST_CA_CRT` and `TRENTO_TEST_CA_KEY` must belong to the same test certificate authority. The workflow uses them to sign the HTTPS certificates configured in the Trento reverse proxy, and the runner trusts `TRENTO_TEST_CA_CRT` before running health checks and Cypress tests.

`TRENTO_TEST_CA_CRT` is public and should be stored as a GitHub Actions variable. It can be imported locally by developers who need to access the generated Trento environments from a browser. `TRENTO_TEST_CA_KEY` is sensitive and should only be stored in GitHub Actions secrets and the team's password vault.

== Usage

=== Running Tests and Provisioning Environments

Manual runs always target an isolated named environment, so they never interfere with the CI deployments:

. Go to **Actions** > **Provision & Test Environment**
. Click **Run workflow**
. Set `environment_name`, which derives the resource group `trento-env-<name>`, the VM name suffix and the Terraform state
. Select the SLES versions you want to deploy to
. Enable `install_rolling` to install from the Trento rolling repository instead of the RPMs in Azure Blob Storage
. Optionally enable `provision_only` to skip the Trento deployment
. Optionally enable `skip_cypress` and `skip_alerting_tests` to skip the Cypress suites (they run by default), set `cypress_spec` to the spec pattern to run (leave empty for the full suite) and `web_ref` to the branch, tag or commit of https://github.com/trento-project/web[trento-project/web] the tests are taken from
. Click **Run workflow**

The workflow creates the resource group, or reuses it if it already exists and is tagged `ManagedBy=trento-installation-automation` (any other existing group makes it fail before touching anything). It then destroys and recreates the Terraform-managed infrastructure and installs Trento. The run summary lists the parameters used, and the run name identifies the environment.

Two behaviors are worth knowing before launching a run:

* The infrastructure is **not** destroyed when the run finishes, so the environment stays available for debugging, even if a step failed. Delete its resource group (`trento-env-<name>`) once you are done.
* Runs of the same environment share a concurrency group. A run in progress is never canceled and a new one waits for it, but GitHub keeps only one pending run per group: if a third run is queued, it replaces the pending one, which is canceled.

=== Choosing which packages to test

Packages present in Azure Blob Storage are installed with the highest repository priority, and every package missing from it is installed from the official SUSE release sources. This is what makes it possible to validate a partial release, for example a release candidate where only `trento-web` is published.

The storage account and container to upload to are configured in the `AZURE_BLOB_STORAGE` and `AZURE_BLOB_STORAGE_CONTAINER` repository variables.

Before launching the workflow, connect to the VPN and, for each SLES version you plan to deploy to, perform the following steps:

. Delete the RPMs left in `<container>/<sles_major_version>/<sp_version>/` by previous runs.
. Upload only the RPMs under validation.

IMPORTANT: Deleting the leftover RPMs is mandatory. The blob-backed repository is configured with priority 1, which `zypper` prefers over the official repositories even if they offer a newer version. An RPM left over from a previous run is repeatedly installed until it is removed from the container.

For example, to validate a `trento-web` release candidate on SLES 15 SP6, leave only `trento-web-*.rpm` in the `15/6/` directory. The remaining packages, `trento-wanda`, `trento-checks`, `trento-agent` and `ansible-trento`, are then installed from the official SUSE release sources.

Every RPM in the container, `ansible-trento-*.rpm` included, is served from a local repository built from the container contents. If the version directory is missing or contains no RPMs, every package is installed from the official SUSE release sources. Enabling `package_source: rolling` ignores Azure Blob Storage entirely and installs everything from the Trento rolling repository.

==== SLES 15 SP4 and the Ansible collection

`ansible-trento` is not officially released for SLES 15 SP4, so release candidate artifacts never include an SP4 build of it. Trento can still be installed on SP4, because the SP4 machine does not use the distribution Ansible. Instead, it creates a Python virtual environment and installs `ansible` 9 with `pip`, and configures it to use the collection provided by the RPM. The collection therefore works regardless of which service pack it was built for.

Recent `ansible-trento` builds require `ansible-linux-system-roles`, which SP4 does not provide. On SP4 the RPM is installed with `rpm --nodeps`, the `suseconnect` role is cloned from Git into a local roles path, and `enable_suseconnect` is set to `false`, because the machines are registered beforehand.

When preparing a run that includes SP4, upload the SP5 `ansible-trento` release candidate to the `15/4/` directory alongside the rest of the SP4 packages.

NOTE: This workaround only exists while SLES 15 SP4 is supported, and can be removed once support ends at the end of 2026.

=== Choosing which Cypress tests to run

The end-to-end tests live in https://github.com/trento-project/web[trento-project/web], and by default they are taken from its default branch. That is only correct when the packages under validation match it. Testing a patch release with tests from the default branch reports false positives, because those tests cover features that the released RPMs do not have yet.

Set `web_ref` to the revision matching the packages under validation. Every release is tagged in the `web` repository, so validating the `3.1.5` patch release means setting `web_ref` to `3.1.5`. Any branch or commit SHA is accepted too, which is useful to try out a test fix before it is merged. Leaving the input empty keeps the default branch, which is what you want when validating rolling packages.

To confirm afterwards which revision produced the results, check the log of the `Checkout Trento Web tests` step, which reports the commit it checked out.

=== Accessing the deployed environments

Because manually dispatched runs leave the infrastructure in place, each machine stays reachable for manual validation at `+https://trento<sles_version>sp<sp_version>-<environment_name>.<azure_region>.cloudapp.azure.com/+`, where `<azure_region>` is the location of the environment resource group (`trento-env-<environment_name>`), which is the one shown in the run summary. For example, https://trento15sp7-foo.westeurope.cloudapp.azure.com/ for SLES 15 SP7 in the `foo` environment.

You can access the deployments using the following methods:

* **Browser**: Import `TRENTO_TEST_CA_CRT` into your browser or system trust store, otherwise the HTTPS certificate is rejected. Log in with the `admin` user and the password stored in `WEB_ADMIN_PASSWORD`.
* **SSH**: Connect as `cloudadmin` with the private key matching `PUBLIC_SSH_KEY_CONTENT`.

The SSH key pair, the test certificate authority and the Trento admin password are all available in the team's password vault.

=== Continuous Integration

The **Continuous Integration** workflow runs on pushes to `main`, pull request open/update events, and manual dispatches. Changes that only touch `+**.adoc+` files or `LICENSE` do not trigger it, since they cannot affect a deployment. It calls the reusable installation base workflow with all supported SLES versions enabled, installs packages from the Trento rolling repository, runs only the `+**/about.cy.js+` Cypress spec against every machine, and destroys the Terraform-managed infrastructure after completion.

=== Cleanup

The infrastructure of the **Continuous Integration** workflow is destroyed by the reusable `terraform-destroy.yml` workflow, which always generates the full machine configuration for every supported SLES version before running `terraform destroy`. It is not meant to be dispatched manually.
